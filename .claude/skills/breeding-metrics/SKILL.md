# 디지털육종 지표·데이터 기준서

템플릿 사이에서 같은 지표가 다른 정의·다른 범위로 나오면 라이브러리 전체의 신뢰가 무너진다. 이 스킬은 모든 템플릿이 공유하는 도메인 기준을 정한다.

## 핵심 규칙

1. **작물·축종을 하나로 고정한다.** 브리프에 없으면 벼(*Oryza sativa*)를 기본으로 쓴다. 염색체 수·게놈 크기가 차트 축과 데이터 분포를 결정하기 때문이다.
2. **값은 카탈로그의 범위 안에서 정한다.** 범위를 벗어나야 하는 시나리오(예: "문제 상황 경보" 데모)라면 명세에 이유를 적는다.
3. **연결된 수치를 계산으로 맞춘다.** 화면에 함께 나오는 숫자는 서로 계산되는 관계여야 한다.
   - ΔG/년 = i · r · σA / L
   - 예측 정확도 r ≈ corr(GEBV, 관측값) / √h²
   - 유의 SNP 수 = 맨해튼 플롯에서 임계선 위 점의 수
   - 선발 비율 p와 선발 강도 i는 정규분포 절단 관계(p=10% → i≈1.755, 5% → 2.063, 1% → 2.665)
4. **통계적으로 가능한 데이터만 만든다.** 상관계수·유전력·빈도는 [0,1] 또는 [-1,1], 귀무가설 아래 p값은 균등분포(QQ 플롯이 대각선을 따름), 유전적 관계 행렬 대각 원소는 1+F.
5. **목업 데이터는 시드 RNG로 생성한다.** `@/lib/rng`의 `createRng(seed)`를 쓰고 시드를 명세에 적는다. 같은 시드면 같은 화면이 나와야 스크린샷 회귀 비교가 가능하다.
6. **단위와 기준 시점을 표기한다.** "ΔG 1.8%/년(2022~2026 평균, 수량 기준)"처럼 무엇을, 언제, 어떤 형질로 쟀는지 밝힌다.

## 목업 데이터 생성 원칙

- 분포를 지정한다: 표현형·GEBV는 정규분포, 콜레이트는 상한이 있는 베타형(대부분 97~99.8%), 처리량은 계절성이 있는 시계열.
- 신호를 심는다: GWAS는 귀무 SNP(균등 p값) 위에 2~5개 QTL 피크를 심고, 피크 주변은 LD로 인해 p값이 함께 낮아지게 한다(거리에 따라 지수 감소).
- 규모를 현실적으로: 맨해튼 플롯은 2만~5만 SNP(ECharts `large` 모드로 렌더 가능), 개체 랭킹 표는 200~2,000개체, 계통도는 3~5세대.
- 이름을 그럴듯하게: 계통명 `YR24-0153`, 품종명은 가상의 한글 이름(실존 품종명을 쓰지 않는다 — 실제 품종 성적처럼 오해받을 수 있다).
- 생성 코드는 명세에 의사코드로 적어 빌더가 그대로 옮길 수 있게 한다.

`docs/specs/{slug}.md`를 다음 구조로 쓴다.

```markdown

## 시각화 구성
| 영역 | 차트/컴포넌트 | 데이터 | 필수 주석(임계선·목표선 등) |

## 수용 기준
- [ ] 검증 가능한 문장으로 5~10개 (예: "임계선 −log10(p)=7.3이 표시되고 그 위 SNP 수가 요약 카드와 일치한다")

## 검산 기록
```

## 명세 검산(명세 모드 필수)

명세의 숫자는 "의도"가 아니라 "생성 규칙을 실행한 결과"여야 한다. 지금까지 명세가 틀린 경우는 모두 같은 원인이었다. 생성 규칙과 수용 기준을 따로 머릿속으로 맞췄기 때문에 실제로 돌리면 어긋났다(목표 λ와 실제 λ, 기본 필터와 "60계통 표시", 기대 지수 범위와 실제 범위, 시드에서 우연히 유의선을 넘는 귀무 SNP).

1. 목업 생성 규칙을 스크래치패드의 작은 Node 스크립트로 옮겨 시드를 고정하고 실행한다. 공통 유틸(`src/lib/rng.ts`, `src/lib/genomics.ts`)이 있으면 같은 알고리즘을 쓴다.
2. 수용 기준·지표 표·결론 문장에 들어가는 모든 숫자를 실행 결과에서 옮겨 적는다. 범위("약 85~120")를 쓰면 실행 결과의 실제 최솟값·최댓값이 그 안에 드는지 확인한다.
3. 기본 상태(기본 필터, 기본 형질, 기본 선발 비율)에서 화면에 보일 결과를 따로 계산한다. 수용 기준은 기본 상태 화면에서 확인 가능해야 한다.
4. 카탈로그 범위를 넘는 값이 나오면(슬라이더 극단값 포함) 규칙을 고치거나, 넘는 것을 의도했다면 화면에 표시할 방법까지 명세에 적는다.
5. 실행 결과를 「검산 기록」 절에 남긴다. 검산을 하지 못한 숫자는 "미검산"이라고 표시한다.
6. 표시값은 원 실행값(5자리 이상)에서 한 번만 표시 자릿수로 반올림한다. 4자리로 적어 둔 값을 다시 3자리로 반올림하면 0.3785 → 0.379처럼 실제(0.378488 → 0.378)와 달라진다(배치 8에서 두 번 발생). 검산 기록에는 원 실행값과 표시값을 함께 적는다.

## 명세 동기화(동기화 모드)

명세는 템플릿을 다시 만들 때의 원본이다. 수정 단계에서 빌더가 데이터·상수를 바꾸거나 검토자가 명세 자체의 오류를 지적했는데 명세를 고치지 않으면, 다음 재생성 때 같은 오류가 되살아난다.

1. 빌더의 `notes`, 검토 보고서(`03_qa_*`, `03_domain_*`)의 "명세" 관련 지적, 템플릿의 `data.ts` 상수를 명세와 대조한다.
2. 코드가 맞고 명세가 틀린 곳은 명세를 코드에 맞춰 고친다. 코드가 틀렸다고 판단되면 명세는 두고 `codeIssues`로 보고한다(코드는 고치지 않는다).
3. 명세 끝에 「변경 이력」 절을 두고 `YYYY-MM-DD 무엇을 왜`를 한 줄씩 적는다.
4. 이 템플릿이 다른 템플릿과 공유될 만한 새 사실을 만들었으면 `references/program-baseline.md`에 한 줄 추가한다.
5. 마지막 검토에서 남은 이슈(minor 포함)를 하나도 빠짐없이 분류한다: 명세를 고쳐 닫음(`changes`), 코드를 고쳐야 함(`codeIssues`), 이번에 안 고침(`deferred`, kind `baseline`·`later`·`wontfix`와 이유). 이미 코드에 반영된 지적은 `changes`에 "이미 반영"으로 적는다. 분류하지 않은 minor는 이월 목록에 그대로 남아, 정리 회차에서 이미 고친 항목을 다시 조사하게 된다(정리 회차 3 계획 항목의 절반이 그랬다).
6. 고치려면 다른 템플릿과 공유하는 기준값(program-baseline의 행, 여러 템플릿이 쓰는 생성 규칙)을 바꿔야 하는 도메인 지적은 이 템플릿에서 고치지 않는다. `docs/backlog/baseline.md`에 한 줄 추가한다: `| 날짜 | 출처 템플릿 | 항목(현재 값 → 바람직한 방향) | 공유하는 템플릿 | 근거 보고서 |`. 명세 「검산 기록」의 알려진 한계에도 적는다. 한 템플릿만 고치면 템플릿 사이 숫자가 어긋나고, 지적이 보고서마다 흩어지면 정리 회차를 시작할 시점을 알 수 없기 때문이다.

## 검토 모드 체크리스트

1. 계산식과 단위가 카탈로그와 같은가
2. 화면의 숫자들이 서로 계산 관계로 맞는가
3. 데이터 분포가 통계적으로 가능한가(QQ 대각선, 범위, 대칭성)
4. 차트 선택이 `visualization-guide.md`의 권장과 맞고 필수 주석이 있는가
5. 용어가 `glossary-ko.md` 표기를 따르는가
6. 명세의 수용 기준을 모두 충족하는가
