# 디자인 회차 운영 자료

오케스트레이터 「디자인 회차」에서 메인이 쓰는 그룹 나누기, 종합·계획 형식, 단계별 브리프 템플릿이다. 1차(2026-10-30~31) `_workspace/07_*`·`08_*` 문서에서 뽑았다.

회차 번호 n은 `_workspace/run_meta.json`에서 `mode: design-review` 기록 수 + 1이다. 1차 파일에는 접미사가 없고(`07_design_review_kpi.md`), 2차부터 `_r{n}`을 붙인다.

## 1. 검토 그룹 나누기

카테고리별로 나누고 한 명이 8개를 넘지 않게 한다. 8개를 넘는 카테고리는 slug 알파벳순으로 반씩 나눈다(1차: viz 11개 → viz-a 6 · viz-b 5). 카테고리 간 검토 1명을 따로 둔다.

재검토(개선 뒤 확인, 2차 이후)는 `docs/backlog/design.md`에 행이 있는 템플릿과 마지막 디자인 회차 뒤 새로 생기거나 바뀐 템플릿만 넣는다. 그룹 나누기는 같다.

B단계 빌더 묶음을 검토 그룹과 같게 나눈다. 검토 보고서 하나를 빌더 한 명이 그대로 읽게 하기 위해서다.

## 2. 검토자 프롬프트에 넣을 것

- 회차 n과 검토 종류(전체 / 재검토), 그룹 이름, `{category}/{slug}` 목록
- 보고서 경로 `_workspace/07_design_review_r{n}_{group}.md`
- 메인이 띄운 개발 서버 base URL, 인스펙터 출력 폴더 `.taste-skill/r{n}/`
- 지난 회차 보고서 경로와 `docs/backlog/design.md`에서 맡은 템플릿 행(재검토면 필수)
- 사용자가 정한 초점(예: "모바일 위주", "업무 화면만")
- 코드를 고치지 않는다는 것, 최종 응답은 짧은 요약(등급·건수·high·`[공통]`·본보기·경로)

## 3. 종합 보고서(메인, `07_design_review_r{n}_summary.md`)

1. **숫자 표**: 그룹별 종합 상·중·하 수, high, medium
2. **high 목록**(`| # | 템플릿 | 지적 | 원인 위치 |`): 메인이 스크린샷·코드로 직접 확인한 것만 high로 둔다. 확인하지 못하면 medium으로 내리고 사유를 적는다. high는 이번 회차에 반드시 고칠 항목이 되므로 오판이면 비용이 크다.
3. **공통 원인 묶음 P1…**(`| 묶음 | 내용 | 관련 지적 | 영향 템플릿 |`): 여러 그룹의 `[공통]`과 공통 문제를 원인별로 묶는다. 고치면 여러 템플릿이 한 번에 나아지는 것을 앞에 둔다.
4. **본보기 패턴**: 검토자가 「본보기」로 표시한 구현. 공통 컴포넌트를 새로 만들 때 기준 구현이 된다.
5. **사용자 결정 필요**: 토큰·팔레트, 이번 회차 범위(공통만 / high까지 / medium까지)
6. **하네스 개선 후보**: verify·lint가 잡을 수 있었는데 못 잡은 것. 회차 뒤 template-qa 스크립트에 반영한다(1차: 카드 밖 텍스트 검사, SVG 11px 미만 검사).
7. **권장 순서**

## 4. 개선 계획(`08_design_fix_plan_r{n}.md`)

- 맨 위: 사용자 결정(날짜와 내용)
- A단계 표(설계자): `| # | 항목 | 해야 할 것 | 근거(묶음·지적 번호) |`
- B단계 표(빌더 묶음): `| 묶음 | 템플릿 | high |`
- 이번에 하지 않는 지적: 「다음 회차」로 적고 회차 끝에 `docs/backlog/design.md`로 옮긴다.
- B단계 진행 중 기록할 「명세 이탈 기록」 절(D단계 입력)

## 5. A단계 설계자 프롬프트 요건

- Skill 도구로 `db-design-system`을 불러와 계약을 지킨다. 바뀐 규칙은 `api-contract.md`, `visual-language.md`, `promotion-holds.md`, template-authoring 「화면 문법」에 함께 반영한다. B단계 빌더가 이 문서들을 읽고 이전한다.
- 기존 공개 API를 깨지 않는다. 새 옵션은 선택값으로 두고, 기본 동작은 계획 표가 요구한 것만 바꾼다.
- 새 공통 컴포넌트는 본보기 구현을 기준으로 만들고, 템플릿 1곳만 옮겨 기준 예시로 남긴다. 나머지는 B단계 빌더가 옮긴다.
- 토큰 색을 바꾸면 `check-palette.mjs`로 전·후를 검산한다.
- 완료 조건: typecheck, build, lint 전체, verify 전체 문제 0건, 바뀐 동작의 대표 화면 스크린샷 직접 확인.
- 보고서 `_workspace/08_architect_design_fix_r{n}.md`: 바뀐 공개 API, B단계 이전 안내(전·후 코드 예시), 화면이 바뀐 템플릿 목록.

## 6. B단계 빌더 브리프 템플릿(`08_phase_b_brief_r{n}.md`)

빌더 묶음이 모두 같은 브리프를 읽는다. 「템플릿마다 할 일」만 회차마다 계획에서 옮겨 적고 나머지는 그대로 쓴다.

```markdown
# 디자인 개선 r{n} B단계 브리프

## 먼저 읽을 것(순서대로)
1. `_workspace/08_architect_design_fix_r{n}.md` — 바뀐 공개 API와 이전 안내
2. `_workspace/08_design_fix_plan_r{n}.md` — B단계 표와 사용자 결정
3. 기준 예시: {A단계에서 옮긴 템플릿 경로}
4. 담당 그룹 검토 `_workspace/07_design_review_r{n}_{group}.md`, 카테고리 간 `…_cross.md`, 인스펙터 결과(있으면)
5. Skill 도구로 `template-authoring`(「화면 문법」)

## 템플릿마다 할 일
{계획에서 옮김: 공통 컴포넌트 이전, high, 이번 범위의 medium}
손대지 않은 지적은 보고에 「다음 회차」로 남긴다.

## 지킬 것
- 담당 템플릿 폴더만 고친다. 공통 모듈(src/design-system, src/charts, src/lib, src/gallery, src/index.css)은 고치지 않고 `[공통]`으로 보고한다.
- 숫자·데이터·생성 규칙은 바꾸지 않는다. 문장을 다시 쓸 때도 숫자는 상수에서 만든다.
- 화면 문구·구성을 명세와 다르게 바꾸면(카드 이동, 문장 삭제, KPI 수 변경) 「명세 이탈」로 보고한다.
- DEV 검산 실패 0을 유지한다. `qa-states.json`이 있으면 상태가 여전히 재현되는지(`expect`) 확인하고, 문구·aria-label을 바꿨으면 상태 단계도 고친다.
- 다른 빌더가 동시에 verify를 돌린다. 일시적 실패는 한 번 다시 돌린다. 직접 띄운 서버는 PID로만 종료하고, 메인이 띄운 서버는 끄지 않는다.

## 완료 조건
- `npm run typecheck` 오류 0, lint 담당 템플릿 오류 0·경고 0, `check-ssr.mjs --slug {담당 slug들}` 실패 0, 담당 템플릿마다 `verify-templates.mjs --slug {slug} --out _workspace/qa` 문제 0건
- 1440-light, 390-light(인포그래픽은 768-light도) 직접 확인

## 보고(마지막 응답)
템플릿별: 고친 항목(high 포함), 「다음 회차」, `[공통]` 요청, 「명세 이탈」, 검증 결과. 짧게.
```

## 7. C단계 `[공통]` 요청 모음(`08_common_requests_r{n}.md`)

`| # | 출처(묶음) | 요청 | 처리 |` 표로 모은다. 다른 빌더를 막는 공통 버그(예: 페이지 폭을 늘리는 컨테이너)는 메인이 바로 고치고 진행 중인 빌더들에게 알린 뒤 「처리」 열에 적는다. 나머지는 B단계가 끝난 뒤 설계자 1회로 처리한다.

## 8. D단계 도메인 검토 입력

- 대상: 문구·숫자·구성이 바뀐 템플릿 전체
- 입력: B단계 보고의 「명세 이탈」 모음(계획 문서의 「명세 이탈 기록」 절), 템플릿 README 변경 이력의 회차 날짜 행
- 확인할 것: 다시 쓴 문구의 용어(glossary-ko), 문장 속 숫자가 상수에서 나오고 실행값과 같은지, visual-language 「기호와 심각도」 준수
- 보고서 `_workspace/08_domain_review_design_r{n}.md`. 같은 분석가가 이어서 동기화 모드로 명세를 고친다(명세 이탈을 명세에 반영).

## 9. `docs/backlog/design.md` 갱신

- 해결한 행을 지우고 맨 아래 「해결」 표(`| 날짜 | 항목 | 해결 회차 |`)로 옮긴다. 표가 없으면 만든다.
- 「다음 회차」로 미룬 지적을 공통·템플릿별 표에 추가한다(출처 보고서와 지적 번호).
- 맨 위 설명의 "디자인 개선 {n+1}차 입력"을 갱신한다.
