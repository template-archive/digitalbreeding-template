# 디자인 검토 절차

자동 검증을 통과한 화면을 사람 눈으로 본다. verify는 넘침·대비·콘솔·카드 밖 텍스트를 잡지만, "가장 중요한 숫자가 먼저 읽히는가", "같은 역할 요소가 템플릿마다 다른가", "선택한 것이 데이터에 묻히는가"는 잡지 못한다. 1차 검토(2026-10-30)에서 33개 템플릿 모두 verify 문제 0건이었는데 high 4건·medium 98건이 나왔다. 이 문서가 그 검토 기준이다.

## 1. 시작 전 확인

1. 프로젝트 기준 문서를 읽는다(이 순서로): `db-design-system/references/visual-language.md`(「앱 화면 규칙」 포함), `api-contract.md`(공통 컴포넌트 옵션), `promotion-holds.md`, `template-authoring/SKILL.md` 「화면 문법」. 규칙을 어긴 것인지 규칙이 없는 것인지 구분해야 고칠 곳이 정해진다.
2. 스크린샷이 최신인지 확인한다: `_workspace/qa/{slug}/1440-light.png` 수정 시각이 템플릿 폴더의 가장 최근 수정보다 늦어야 한다. 아니면 `node .claude/skills/template-qa/scripts/verify-templates.mjs --slug {a,b,…} --out _workspace/qa`로 다시 만든다.
3. `docs/backlog/design.md`와 지난 회차 보고서에 맡은 템플릿의 행이 있으면 먼저 해결 여부를 판정한다.

## 2. 보는 관점 8가지

| # | 관점 | 확인할 것 |
| --- | --- | --- |
| 1 | 시각 위계 | 첫 화면에서 가장 중요한 숫자·결론이 먼저 읽히는가. 제목·부제·설명 문단이 핵심을 밀어내지 않는가. 모든 것이 같은 무게인 평평한 화면 |
| 2 | 밀도와 여백 | 판독이 어려울 만큼 빽빽한 곳, 반대로 크게 빈 영역(옆 카드 높이로 늘어난 카드), 카드 높이 불균형, 정렬 어긋남, 격자 리듬 |
| 3 | 차트 선택과 판독성 | 데이터 유형에 맞는 차트인가, 범례·축·단위·라벨이 충분한가, 색만으로 구분하는가(모양·라벨 병행), 강조색이 한 가지 의미로 쓰이는가, 계열이 너무 많지 않은가, 선택 표시가 데이터에 묻히지 않는가 |
| 4 | 타이포그래피 | 핵심 정보가 지나치게 작은 글자에 있지 않은가, 숫자 정렬(tabular-nums·오른쪽 정렬), 줄 길이, 어색한 줄바꿈(낱말 중간 끊김) |
| 5 | 색과 상태 | 의미 색(경보·주의·양호·정보)이 일관되는가, 다크 모드에서 너무 밝거나 탁한 곳, 배지·칩 남용, ▲▼가 증감 외 뜻으로 쓰이는가 |
| 6 | 상호작용 어포던스 | 누를 수 있는 것이 누를 수 있어 보이는가, 선택 상태가 분명한가, 상태 화면(선택·경고·입력 오류)이 이해되는가, 390px 터치 대상 44px·간격 8px, Shift·Ctrl 전용 조작 |
| 7 | 모바일·태블릿 구성 | 390/768px에서 정보 순서가 합리적인가(중요한 것이 아래로 밀리지 않는가), 표가 가로 스크롤로만 남아 쓸모없어지지 않는가, 결론 열이 스크롤 끝에 숨지 않는가, 인포그래픽 축소 배율이 판독 가능한가 |
| 8 | 카테고리 안 일관성 | 같은 카테고리끼리 머리 구성, KPI 줄, 섹션 제목, 카드, 범례 위치, 저장·확정 방식이 같은 문법인가 |

일반 UI/UX 기준은 ui-ux-pro-max의 「Data-Dense Dashboard」(대비 4.5:1, 포커스 링, 색 외 구분, 터치 44px, 본문 줄 높이 1.5~1.75, 애니메이션 150~300ms·reduced-motion, 데이터에 맞는 차트·표 대체)를 따른다. 프로젝트 규칙과 다르면 프로젝트 규칙이 우선이다.

## 3. 자료와 도구

- 스크린샷: `_workspace/qa/{slug}/{390|768|1440}-{light|dark}.png`(전체 페이지), 상태 화면 `{폭}-light-{state}.png`. 최소 1440-light, 1440-dark, 768-light, 390-light를 열고 상태 화면이 있으면 하나 이상 연다. 인포그래픽은 768-light(잘림 → 요약 카드)를 꼭 본다.
- 코드: `src/templates/{category}/{slug}/`. 지적 위치를 `파일:줄`로 적기 위해 읽는다.
- 동작 확인: 프롬프트로 받은 base URL의 `#/t/{category}/{slug}`를 playwright로 열어 호버·포커스·탭을 확인한다. 서버를 직접 띄웠으면 PID로만 종료한다. 화면 구석의 「피드백」 도구(`src/features/feedback`)와 상세 화면의 미리보기 프레임·가져오기 모달은 갤러리 기능이라 템플릿 검토 대상이 아니다(verify·썸네일에서도 숨김). 템플릿만 보려면 `?embed=1`로 연다.
- tasteskill 인스펙터(앱 모드, 있으면):
  ```bash
  mkdir -p .taste-skill/r{n} && node ~/.claude/skills/design-taste-frontend/scripts/inspect.mjs "{baseUrl}/?embed=1#/t/{category}/{slug}" --app --out .taste-skill/r{n}/{slug} > .taste-skill/r{n}/{slug}.txt
  ```
  FAIL·WARN은 보조 근거다. 1차에서 정한 해석: `numeric-align` 수치는 화면 낭독기용 숨은 표까지 세서 부풀려지므로 보이는 셀 기준으로 판단한다. 인포그래픽 큰 숫자(48~72px)는 인쇄 포스터 규격이라 `kpi-size` 예외다. ♀·♂는 교배 부모 표기 관례라 `emoji` 예외다. 가로 스크롤 가장자리 페이드는 기능적 scrim이라 `gradient` 예외다. 예외는 지적하지 않는다.

## 4. 심각도

| 심각도 | 기준 | 예 |
| --- | --- | --- |
| high | 화면 목적을 해친다 | 핵심 숫자·결론이 안 읽힘, 차트가 오해를 부름, 모바일에서 주요 기능을 쓸 수 없음, 선택 상태를 알 수 없음, 경보 타일이 보통 타일과 똑같이 보임 |
| medium | 판독·사용을 눈에 띄게 방해하지만 목적은 달성 | 위계 약함, 밀도 과다, 일관성 깨짐, 작은 터치 대상, 결론 열이 스크롤 끝에 숨음 |
| low | 다듬기 | 간격, 정렬, 문구 길이, 미세한 색 |

## 5. 지적 작성 규칙

- 근거: 스크린샷 파일명과 화면 위치(예: `390-light.png 상단 KPI 2열`) 또는 `파일:줄`. 근거 없는 지적은 쓰지 않는다.
- 고침 방향은 한 줄로, 빌더가 그대로 작업 지시로 쓸 수 있게 쓴다. 공통 컴포넌트에 이미 옵션이 있으면 그 이름을 쓴다(예: `DataTable hideBelow`).
- 원인이 공통 모듈(`src/design-system`, `src/charts`, `src/index.css`)이면 `[공통]`, 토큰·팔레트를 바꿔야 하면 `사용자 결정`, 차트 형태 변경이 도메인 의미를 바꿀 수 있으면 `도메인 확인`을 붙인다.
- 같은 문제가 그룹 안 여러 템플릿에 있으면 템플릿마다 반복하지 말고 「요약」의 공통 문제로 한 번 쓰고 템플릿 표에는 번호만 참조한다.
- 장점을 템플릿마다 한두 줄 적고, 다른 템플릿이 따를 만하면 「본보기」로 표시한다.

## 6. 보고서 형식(그룹 검토)

```markdown
# 디자인 검토 r{n}: {그룹}

| 출처(지난 보고서 # 또는 backlog 행) | 판정(해결·일부·남음) | 근거 |

## 요약
- 그룹 전체 인상 2~4줄
- 공통 문제(여러 템플릿에 반복) — C1, C2 … 번호를 붙인다
- 다른 그룹과 맞춰야 할 것으로 보이는 패턴

## {slug} — {한국어 제목}
- 종합: 상/중/하 · 한 줄 평
- 장점: … (본보기면 표시)
| # | 심각도 | 관점(1~8) | 지적 | 근거 | 고침 방향 |
| --- | --- | --- | --- | --- | --- |

## notes
- 인스펙터 생략·서버 접속 실패·「확인 필요」 사유 등
```

## 7. 카테고리 간 검토

- 자료: 갤러리 썸네일 `src/gallery/thumbs/{category}-{slug}-{light|dark}.webp`(임베드 1440 첫 화면 900px를 줄인 것, Read로 바로 열린다)를 카테고리별로 모두 연다. 썸네일이 템플릿보다 오래됐으면 메인에게 알리고(재생성은 `gen-thumbs.mjs`), 그동안은 `_workspace/qa/{slug}/1440-light.png` 위쪽을 본다.
- 코드 grep으로 같은 역할의 로컬 구현 개수를 센다(예: 템플릿이 직접 만든 결론 띠·요약 타일·저장 바). 개수가 승격 판단의 근거가 된다.
- 보는 것: 머리(제목·범위·기준일·필터 배치), KPI 줄, 결론 위치, 차트 카드 안 범례 위치, 각주, 저장·확정 방식, 선택 표시, 다크 모드 단계.
- 형식: 「잘 맞는 것」 목록 + 「어긋나는 것」 표(`| # | 심각도 | 지적 | 근거 | 고침 방향 |`, 번호 X1, X2 …).
