# 템플릿 허브 로그인(메일 코드) — 설계

- 날짜: 2026-11-03
- 관련 설계: `docs/superpowers/specs/2026-11-03-hub-requests-design.md`(작업 요청). 이 문서가 그 기능의 「요청 만들기」에 필요한 로그인을 정한다.
- 운영 사이트: https://digitalbreeding-template.vercel.app (공개, 누구나 열 수 있음)

## 1. 왜 만드나

허브에서 만든 요청은 GitHub 이슈가 되고, 결국 누군가의 작업 시간과 Claude 사용량으로 이어진다. 그래서 요청은 **사내 직원만** 만들 수 있어야 한다. 반면 템플릿 보기·다운로드·피드백·요청 목록 보기는 지금처럼 **누구나** 할 수 있어야 한다.

사내 메일은 시놀로지 MailPlus이고, 허브 관리자는 그 메일 서버를 설정할 수 없다. 사내 SSO나 디렉터리도 쓸 수 없다. 그래서 "회사 메일함을 열 수 있는 사람 = 직원"으로 본다. 회사 메일로 코드를 보내고, 그 코드를 입력하면 로그인된다.

### 사용자가 정한 것

| 결정 | 이유·조건 |
| --- | --- |
| 허브에 회원가입·로그인을 만든다(Vercel 배포 보호 대신) | 운영 사이트는 공개로 둔다 |
| 가입은 사내 직원만 | 회사 메일 도메인으로 판단한다 |
| 화면에는 회사 이름이 드러나지 않게 한다 | 직원 판단은 서버(백엔드)에서만 한다 |
| 조회는 누구나, **요청 만들기만** 로그인이 필요하다 | |
| 코드 메일은 허브 전용 Gmail 계정의 SMTP로 보낸다(선택지 A) | 회사 메일 서버를 설정할 수 없다. 무료이고, 발신 주소가 `…@gmail.com`이라 회사 이름이 드러나지 않는다 |
| 나중에 도메인이 생기면 다른 발송 서비스로 옮길 수 있게 한다 | 발송 부분을 떼어 두고 설정만 바꾼다(5.5) |
| 운영 계정 데이터와 Gmail 앱 비밀번호는 운영 배포에만 둔다 | 미리보기는 PR 브랜치 코드를 그대로 실행하므로, 같이 두면 PR을 올릴 수 있는 사람 누구나 읽을 수 있다(5.3) |

## 2. 누가 어떻게 쓰나

- **직원**: 「로그인」 → 회사 메일 주소 → 메일로 온 6자리 코드 → 완료. 처음이면 표시 이름을 한 번 입력하고, 그 순간 가입된다. 비밀번호는 없다.
- **직원이 아닌 사람**: 로그인 화면은 똑같이 보인다. 코드 메일만 오지 않는다(4.2). 로그인하지 않아도 보기 기능은 모두 쓸 수 있다.
- **관리자**(저장소 소유자): 환경 변수와 Gmail 계정을 관리한다. 관리 화면은 없다. 계정 정리가 필요하면 DB에서 직접 한다(`docs/hub-auth.md`에 방법을 적는다).

## 3. 흐름

1. 로그인하지 않은 사람이 「작업 요청 보내기」나 「새 템플릿 요청」을 누른다. 또는 사이드바의 「로그인」을 누른다.
2. 로그인 창(1단계): 메일 주소를 입력하고 「코드 받기」를 누른다.
3. 서버가 주소를 확인한다. 허용 도메인이면 6자리 코드를 만들어 메일로 보낸다. 허용 도메인이 아니면 아무것도 보내지 않는다. **두 경우 모두 응답과 화면은 같다**: "코드를 보냈습니다. 메일이 오지 않으면 주소를 확인해 주세요."
4. 로그인 창(2단계): 코드를 입력한다. 처음 로그인하는 주소면 표시 이름 칸이 함께 나온다.
5. 맞으면 세션 쿠키가 생기고 창이 닫힌다.
   - 요청 버튼에서 시작했으면 쓰던 요청 양식이 그대로 열린다.
   - 사이드바에서 시작했으면 원래 화면에 머문다.
6. 사이드바 아래에 표시 이름과 「로그아웃」이 보인다. 이름을 누르면 표시 이름을 바꿀 수 있다.

## 4. 목표 · 비목표 · 반목표

**목표**
- A1. 메일 코드 로그인과 첫 로그인 가입(표시 이름)
- A2. 서버에서만 하는 직원 판단(허용 도메인 환경 변수)
- A3. 세션 쿠키, 로그아웃, 표시 이름 변경
- A4. 로그인이 필요한 동작에서 로그인 창을 띄우고, 로그인 후 하던 동작으로 돌아가기
- A5. 교체할 수 있는 메일 발송(지금은 Gmail SMTP, 로컬 개발은 터미널 출력)
- A6. 남용 방지(코드 시도 횟수, 발송 수 제한)
- A7. 관리자용 설정 안내 문서 `docs/hub-auth.md`

**비목표(이번에 하지 않음)**
- 관리자 화면, 계정 정지·삭제 기능, 역할·권한 등급
- 비밀번호 로그인, 소셜 로그인, 사내 SSO
- 피드백 코멘트를 계정에 연결하기(피드백은 지금처럼 익명)
- GitHub 계정과 허브 계정 연결
- 도메인 메일(Resend 등)로 실제 전환. 설정만으로 바꿀 수 있게만 해 둔다

**반목표(이렇게 되면 기능이 돌아가도 실패)**
- 회사 이름이나 메일 도메인이 화면, 공개 JS 번들, API 응답, 오류 문구, 코드 메일 본문 어디에든 나타난다
  - 대상은 시스템이 내보내는 값(설정값, 고정 문구, 메일)이다. 직원이 요청·코멘트에 직접 쓴 글이나 GitHub 프로필은 대상이 아니다. 대신 요청 양식에 "누구나 볼 수 있다"는 안내를 둔다(작업 요청 설계 5.4)
- 허용되지 않은 도메인 주소로 계정이 생기거나 세션이 생긴다
- 로그인 기능의 장애(메일 실패, 설정 누락, DB 오류)가 템플릿 보기·다운로드·피드백을 막는다
- 허브가 남의 메일함에 코드 메일을 퍼붓는 도구가 된다
- 코드·세션 토큰이 원문으로 DB나 로그에 남는다
- Gmail 계정 비밀번호(앱 비밀번호)가 브라우저로 내려가거나 저장소에 들어간다
- 미리보기 배포(PR 브랜치 코드)가 운영 계정 데이터나 Gmail 앱 비밀번호를 읽을 수 있다

## 5. 설계

### 5.1 서버 API

기존 피드백 API와 같은 방식으로 만든다. Vercel 함수(`api/`)와 Vite 개발 미들웨어(`vite.config.ts`)에 함께 달고, 구현은 `server/` 아래에 둔다. 응답 머리글(`Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`)과 본문 읽기·크기 제한도 피드백 처리기와 같게 한다.

| 요청 | 하는 일 |
| --- | --- |
| `POST /api/auth/code` `{ email }` | 주소를 정규화하고 허용 도메인이면 코드를 만들어 보낸다. 허용 여부와 관계없이 같은 200 응답. 발송 수 제한에 걸리면 429, 메일 발송이 실패하면 503 |
| `POST /api/auth/verify` `{ email, code, name? }` | 코드를 확인한다. 기존 사용자면 세션을 만든다. 새 사용자인데 `name`이 없으면 코드를 소비하지 않고 `{ needsName: true }`를 돌려준다. `name`과 함께 다시 보내면 계정과 세션을 만든다 |
| `GET /api/auth/me` | `{ user: { id, name } \| null }`. 세션을 연장한다(5.3) |
| `POST /api/auth/name` `{ name }` | 로그인한 사람의 표시 이름 변경 |
| `POST /api/auth/logout` | 세션 삭제, 쿠키 만료 |

- **쓰기 요청 보호**: 모든 POST는 피드백 API와 같은 같은 출처 확인(`Origin`이 현재 호스트, `Sec-Fetch-Site`가 cross-site가 아님)을 한다.
- **메일 주소 정규화**: 앞뒤 공백 제거, 소문자. 형식이 메일 주소가 아니면 400("메일 주소 형식을 확인해 주세요"). 이 문구도 도메인을 언급하지 않는다.
- **응답에 넣지 않는 것**: 메일 주소(본인 것 포함), 허용 도메인, 가입 여부(4.2의 같은 응답 규칙). `me`는 `id`와 표시 이름만 돌려준다.
- **다른 서버 코드에서 쓸 함수**: `requireUser(request)` → 세션이 유효하면 `{ id, name }`, 아니면 401 오류. 작업 요청 API(`POST /api/requests`)가 이것을 쓴다.

### 5.2 직원 판단

- 서버 환경 변수 `AUTH_ALLOWED_DOMAINS`에 허용 도메인을 쉼표로 적는다. 메일 주소의 `@` 뒤가 목록의 한 항목과 **정확히** 같아야 한다. 하위 도메인은 따로 적어야 허용된다.
- 이 값은 서버에서만 읽는다. `VITE_` 접두사를 붙이지 않고, 클라이언트 코드는 이 값을 알 수 없다.
- 설정이 없으면 로그인을 닫는다. 코드 요청은 503("로그인을 아직 사용할 수 없습니다"), 다른 보기 기능은 그대로다.
- 저장소의 코드·문서·테스트에는 실제 회사 도메인을 쓰지 않는다. 테스트는 `example.test` 같은 가짜 도메인을 쓴다.

#### 허용되지 않은 주소에 같은 응답을 주는 이유

"사용할 수 없는 주소입니다"라고 답하면, 여러 도메인을 넣어 보는 것만으로 어느 회사의 허브인지 알아낼 수 있다. 같은 응답을 주면 직원이 아닌 사람은 메일을 기다리다 끝나지만, 이 허브의 사용자는 직원이므로 손해가 작다. 직원이 주소를 잘못 쓴 경우에도 어차피 서버는 메일함이 실제로 있는지 모른다. 그래서 두 경우를 구분해 얻는 이득이 없다(제 판단).

**숨기는 수준(제 판단)**: 화면에 보이는 것만 같게 하는 가벼운 숨김이다. 응답 시간이나 드문 오류까지 비교하며 작정하고 떠보는 사람은 막지 않는다. 그것까지 막으려면 발송 실패를 직원에게도 알릴 수 없게 되는데, 이 허브에서 숨기는 정보(어느 회사의 허브인지)에 비해 손해가 크다. 그래서 다음 범위까지만 맞춘다.
- 응답 문구와 상태 코드: 허용 여부와 관계없이 같다. 예외는 실제 발송 실패(503)와 전체 하루 한도(429)뿐이다.
- 같은 주소 제한(60초·시간·하루): 허용되지 않은 주소에도 똑같이 센다. 코드 행이 아니라 쓰기 제한 표로 센다.
- 코드 확인 실패 문구: 코드 없음·만료·틀림·5회 초과를 모두 "코드가 맞지 않거나 만료되었습니다. 코드를 다시 받아 주세요"로 같게 한다.

### 5.3 코드·세션

**코드**
- 6자리 숫자(`crypto.randomInt`), 10분 유효.
- 한 주소에 유효한 코드는 하나뿐이다. 새로 받으면 이전 코드는 무효가 된다.
- 다시 받기는 60초 뒤부터 된다. 화면에 남은 초를 보인다.
- 틀린 시도가 5번이면 그 코드는 무효가 된다. 다시 받아야 한다.
- DB에는 `HMAC-SHA256(AUTH_SECRET, 주소 + 코드)`만 저장한다. 코드가 6자리라 단순 해시는 DB가 유출되면 바로 풀린다. 비밀 키를 섞으면 키 없이는 풀 수 없다.
- 확인에 성공하면 코드를 지운다.

**세션**
- 무작위 32바이트 토큰을 쿠키에 담고, DB에는 그 SHA-256 해시만 저장한다.
- 쿠키 `db_hub_session`: `HttpOnly; SameSite=Lax; Path=/api; Secure`(HTTPS일 때).
  - `Path=/api`로 두는 이유: 화면 쪽 JS는 쿠키를 읽을 필요가 없고, 로그인 여부는 `/api/auth/me`로 묻는다.
- **유지 기간**: 마지막 사용 뒤 30일. 쓰는 동안 연장하되, 처음 로그인한 뒤 90일이 지나면 다시 로그인해야 한다.
  - 90일 상한을 두는 이유: 퇴사자는 회사 메일을 잃지만 이미 받은 세션은 남는다. 상한이 없으면 계속 쓰는 한 세션이 끝나지 않는다(제 판단).
- 연장은 `me`와 `requireUser`가 할 때마다가 아니라 하루에 한 번만 DB에 쓴다.

**환경 분리(사용자 결정: 운영 비밀은 운영에만)**

미리보기 배포는 PR 브랜치의 코드를 그대로 실행한다. 그래서 운영 계정 데이터와 비밀값을 미리보기가 읽을 수 있으면, PR을 올릴 수 있는 사람은 누구나 직원 메일 목록을 읽거나 운영 세션을 꾸며 낼 수 있다.

| | 운영(Production) | 미리보기(Preview)·로컬 |
| --- | --- | --- |
| 계정·코드·세션 표 | **운영 전용 DB** `AUTH_DATABASE_URL`(Production에만 설정) | 기존 `DATABASE_URL`, `scope = 'preview'` |
| `AUTH_SECRET` | 운영 값 | 별도 값(운영 값과 달라야 함) |
| 코드 메일 | Gmail SMTP(`SMTP_*`는 Production에만 설정) | console: 코드를 Vercel 함수 로그(로컬은 터미널)에 출력 |

- 운영에서 `AUTH_DATABASE_URL`이 없으면 로그인을 닫는다(503). `DATABASE_URL`로 넘어가지 않는다. 운영 표가 미리보기와 같은 DB에 생기는 일을 막기 위해서다.
- 미리보기는 원래 Vercel에 로그인한 팀원만 열 수 있다. 그 사람들은 함수 로그도 볼 수 있으므로, 미리보기 로그인 시험은 로그에서 코드를 보고 한다.
- 미리보기와 로컬은 `preview` 범위 하나를 함께 쓴다(제 판단). 브랜치마다 나누면 미리보기마다 다시 가입해야 한다.
- 실제 이슈 생성은 작업 요청 설계대로 운영에서만 한다.

### 5.4 데이터(Neon Postgres)

운영은 `AUTH_DATABASE_URL`의 전용 DB, 미리보기·로컬은 기존 `DATABASE_URL`에 표를 둔다(5.3). 표 만들기는 피드백처럼 서버가 처음 쓸 때 `CREATE TABLE IF NOT EXISTS`로 한다. 쓰기 제한 표(`feedback_rate_limits`)는 각 환경이 쓰는 DB에 함께 둔다.

| 표 | 칸 |
| --- | --- |
| `hub_users` | `id`(무작위, 외부에 보이는 유일한 식별자), `scope`, `email`(정규화), `name`, `created_at`, `last_login_at`. `(scope, email)` 유일 |
| `hub_login_codes` | `scope`, `email`, `code_hash`, `expires_at`, `attempts`, `sent_at`. `(scope, email)` 기본 키 |
| `hub_sessions` | `token_hash`(기본 키), `scope`, `user_id`, `created_at`, `last_seen_at` |

- 메일 주소는 원문으로 저장한다. 관리자가 문제 계정을 찾으려면 필요하다. API 응답에는 넣지 않는다.
- 만료된 코드·세션은 피드백의 쓰기 제한 표처럼 가끔 정리한다.
- 표시 이름: 앞뒤 공백을 빼고 1~20자. 제어 문자는 막는다. 같은 이름은 허용한다.

### 5.5 메일 발송

- 발송은 `sendLoginCode(to, code)` 하나를 가진 모듈 뒤에 둔다. 구현은 두 가지다.
  - **smtp**: `nodemailer`(새 의존성). 설정 `SMTP_HOST`(기본 `smtp.gmail.com`), `SMTP_PORT`(기본 465), `SMTP_USER`, `SMTP_PASS`(Gmail 앱 비밀번호), `MAIL_FROM`(기본 `SMTP_USER`), `MAIL_FROM_NAME`(기본 「템플릿 허브」).
  - **console**: 코드를 서버 로그(미리보기는 Vercel 함수 로그, 로컬은 터미널)에 출력한다. 운영이 아닐 때만 쓴다. 운영에서 SMTP 설정이 없으면 console로 넘어가지 않고 503이다.
  - 운영이 아니어도 `SMTP_USER`가 있으면 smtp를 쓴다. 메일 도착 시험(6절 0단계)에만 쓰고, 평소 미리보기에는 넣지 않는다.
- **다른 서비스로 옮기기**: Resend·SES 같은 서비스도 SMTP를 제공한다. 그래서 도메인이 생기면 `SMTP_*`와 `MAIL_FROM`만 바꾸면 된다. 서비스 전용 API가 필요해지면 같은 모듈에 구현을 하나 더한다.
- **메일 내용**
  - 제목: `[템플릿 허브] 로그인 코드 123456`
  - 본문: 코드, 10분 유효, "직접 요청하지 않았다면 이 메일을 무시하세요", 허브 주소.
  - 일반 텍스트와 간단한 HTML을 함께 보낸다.
  - 회사 이름·도메인·받는 사람 주소는 본문에 넣지 않는다.
- 발송이 실패하면 저장한 코드를 지우고 503("코드 메일을 보내지 못했습니다. 잠시 후 다시 시도해 주세요")을 돌려준다. 서버 로그에는 오류 종류만 남기고 주소·코드는 남기지 않는다.

### 5.6 남용 방지

기존 `limitRequests`를 쓴다. 지금은 1분 창만 있으므로, 작업 요청 설계와 같이 창 길이(분·시·일)를 받도록 넓힌다. 한 번만 넓혀 두 기능이 같이 쓴다.

| 대상 | 한도(제 판단) |
| --- | --- |
| 코드 요청, 같은 주소 | 60초에 1번, 시간당 5번, 하루 10번 |
| 코드 요청, 같은 IP | 시간당 20번 |
| 코드 발송, 전체 | 하루 300통(Gmail 일반 계정 하루 한도 약 500통보다 낮게) |
| 코드 확인, 같은 IP | 분당 10번 |

- 허용되지 않은 주소의 요청도 IP 한도에 센다. 메일은 보내지 않는다.
- 한도에 걸리면 429와 기다릴 시간을 돌려준다. 화면 문구는 "잠시 후 다시 시도해 주세요".

### 5.7 화면

갤러리 셸 규칙(`db-design-system`의 `references/api-contract.md` 「갤러리 셸·상세 화면」)과 디자인 토큰을 따른다. 390·768·1440, 라이트·다크, 키보드·스크린리더를 지원한다.

- **로그인 상태**: 화면 쪽에 `useAuth()`(현재 사용자, 로그인 창 열기, 로그아웃)를 두고 앱 시작 때 `/api/auth/me`를 한 번 부른다. 실패하면 "로그인 안 됨"으로 보고, 다른 화면은 영향을 받지 않는다.
- **사이드바**
  - 아래쪽에 「로그인」 버튼을 둔다. 로그인하면 표시 이름(누르면 이름 변경)과 「로그아웃」이 보인다.
  - 1024px 미만에서는 메뉴 시트 안에 같은 항목을 둔다.
- **로그인 창**
  - 기존 모달과 같은 방식이다(포커스 가둠, Esc로 닫기, 닫으면 여는 버튼으로 포커스 복귀).
  - 1단계: 「메일 주소」 칸, 「코드 받기」.
  - 2단계: 「6자리 코드」 칸(`inputmode=numeric`, `autocomplete=one-time-code`), 처음이면 「표시 이름」 칸, 「다시 받기(n초)」, 「주소 바꾸기」.
  - 안내 문구는 일반적인 말만 쓴다(예: "업무용 메일 주소로 로그인합니다"). 회사 이름, 도메인, 예시 주소의 회사 도메인은 쓰지 않는다.
- **로그인이 필요한 동작**
  - `requireLogin(이어서 할 일)`로 감싼다. 로그인하지 않았으면 로그인 창을 열고, 성공하면 이어서 할 일을 실행한다.
  - 요청 양식에 쓰던 내용은 로그인 창을 거쳐도 남는다.
- 로그인 기능이 꺼져 있으면(503) 「로그인」 버튼을 누를 때 "로그인을 아직 사용할 수 없습니다"를 보인다. 버튼을 숨기지는 않는다.

### 5.8 소유자가 한 번 할 설정(코드 밖)

1. 허브 전용 Gmail 계정을 만들고 2단계 인증을 켠 뒤 앱 비밀번호를 만든다.
2. 운영 전용 Neon DB(같은 Neon 프로젝트의 새 데이터베이스나 새 프로젝트, 무료 범위)를 만든다.
3. Vercel 환경 변수를 넣는다.
   - **Production에만**: `AUTH_DATABASE_URL`, `SMTP_USER`, `SMTP_PASS`, 필요하면 `MAIL_FROM_NAME`
   - **Production·Preview 각각 다른 값**: `AUTH_SECRET`(무작위 32바이트 이상)
   - **둘 다 같은 값**: `AUTH_ALLOWED_DOMAINS`
4. 로컬 `.env`에는 `AUTH_ALLOWED_DOMAINS`와 로컬용 `AUTH_SECRET`만 넣는다. 코드는 터미널에 출력된다.

## 6. 검증·완료 기준

- **0단계: 메일 도착 시험(구현 전에 먼저)**
  - Vercel 함수에서 Gmail SMTP로 회사 주소에 코드 메일을 보낸다. 시험 브랜치 하나에만 `SMTP_USER`·`SMTP_PASS`를 브랜치 지정 Preview 변수로 잠시 넣고, 시험이 끝나면 지운다.
  - 확인할 것: 발송 성공(Gmail이 클라우드 서버의 로그인을 막지 않는지), 1분 안에 받은편지함 도착(스팸함 아님).
  - 실패하면 구현을 멈추고 사용자와 다른 발송 방법(B·C)을 다시 정한다.
  - 시험 경로는 시험 후 지운다.
- **단위 테스트**(`node --test`, `test:feedback`에 포함)
  - 주소 정규화와 도메인 판정: 대소문자, 공백, 하위 도메인, `+` 주소, 형식 오류
  - 같은 응답 규칙: 허용되지 않은 주소면 응답은 같고 발송 함수는 호출되지 않는다
  - 코드: 만료, 5번 실패 무효, 새 코드가 이전 코드를 무효화, 60초 재발송 제한, HMAC 저장
  - 세션: 생성, 30일 만료, 90일 상한, 하루 한 번 연장, 로그아웃
  - 새 사용자 `needsName` 흐름: 이름 없이 확인하면 코드가 소비되지 않는다
  - 쓰기 제한 창(분·시·일)
- **처리기 테스트**: 메일 발송과 DB를 가짜로 바꿔서 확인한다.
  - 같은 출처가 아니면 403
  - 쿠키 속성
  - 응답에 메일 주소·도메인이 없다
  - SMTP 설정이 없을 때: 운영 503, 미리보기·로컬 console
  - 운영에서 `AUTH_DATABASE_URL`이 없으면 503이고 `DATABASE_URL`을 쓰지 않는다
  - `AUTH_ALLOWED_DOMAINS`가 없으면 503이고 피드백 API는 정상
- **번들 점검**: `npm run build` 결과물(`dist/`)에 `AUTH_ALLOWED_DOMAINS`·`SMTP_` 같은 서버 전용 이름이나 값이 없는지 확인한다. 방법은 빌더가 정한다.
- **화면 점검**: 로그인 창 두 단계와 사이드바(로그인 전·후)를 390·768·1440 × 라이트·다크로 연다. 가로 넘침 0, axe 위반 0, 키보드만으로 로그인할 수 있어야 하고, 스크린샷을 남긴다.
- **종단 시나리오**
  - 미리보기 배포에서 1~5를 한다. 코드는 Vercel 함수 로그에서 본다.
  - 운영에 배포한 뒤에는 1~3만 실제 회사 메일로 한 번 더 확인한다.

  1. 회사 주소로 코드를 받는다.
  2. 처음 로그인하며 이름을 정한다.
  3. 로그아웃 뒤 다시 로그인한다(이름을 묻지 않는다).
  4. 허용되지 않은 주소는 같은 문구를 보이고, 코드가 만들어지지 않는다(로그에도 없다).
  5. 틀린 코드를 5번 넣으면 무효가 된다.

## 7. 단계와 작업 요청 설계와의 관계

로그인은 작업 요청 설계 7절의 단계보다 먼저 하는 **0단계, PR 하나**다.

1. 메일 도착 시험(6절 0단계)
2. 서버(코드·세션·발송·쓰기 제한 창 넓히기)와 테스트
3. 화면(사이드바, 로그인 창, `useAuth`·`requireLogin`)과 화면 점검
4. `docs/hub-auth.md`

작업 요청 설계에서 로그인에 맞춰 바뀌는 부분(그 문서에 반영함):
- `POST /api/requests`는 `requireUser`가 필수다. 쓰기 제한은 익명 쿠키가 아니라 계정 기준이다.
- 요청자 이름 칸을 없애고, 로그인한 사람의 표시 이름을 쓴다. 이슈 메타 주석에 허브 사용자 `id`를 넣는다.
- 피드백 코멘트, 요청 목록·상세 보기, 「가져가기」 안내는 로그인 없이 그대로다.

## 8. 빌더에게 맡기는 것

- API 경로를 함수 파일 하나로 묶을지 나눌지(Vercel 함수 개수), 처리기 구조
- `needsName` 흐름의 세부(같은 요청 재전송 또는 짧은 가입 표)
- 정확한 화면·메일 문구(이 문서의 문구는 의도), 갤러리 규칙 안의 세부 디자인
- 만료 데이터 정리 주기, 번들 점검 방법, 메일 도착 시험 방법

## 9. 제 판단으로 정한 것(확인 필요)

- 허용되지 않은 주소에도 "코드를 보냈습니다"와 같은 응답(도메인 추측 방지). 화면에 보이는 것만 같게 하고, 응답 시간·발송 실패 503은 막지 않는다(5.2)
- 회사 이름 숨김은 시스템이 내보내는 값에만 적용한다. 직원이 쓴 글과 GitHub 프로필은 대상이 아니다
- 코드 6자리·10분·5회·재발송 60초, HMAC 저장
- 세션 30일(사용 시 연장), 처음 로그인 후 90일이면 다시 로그인
- 미리보기와 로컬은 계정을 함께 쓴다(`preview` 하나), 운영과는 분리
- 발송 한도: 주소당 시간 5·하루 10, IP당 시간 20, 전체 하루 300통. 확인은 IP당 분 10번
- 메일 주소는 DB에 원문으로 저장하되 어떤 응답에도 넣지 않는다(본인에게도)
- 표시 이름 1~20자, 중복 허용, 계정 메뉴에서 변경 가능
- 이슈에는 요청자 메일 주소를 넣지 않고 표시 이름과 허브 사용자 id만 넣는다
- 로컬 개발은 SMTP 없이 터미널에 코드 출력

## 10. 결정 기록

- 2026-11-03 사용자 결정: 운영 계정 데이터와 Gmail 앱 비밀번호는 운영 배포에만 둔다. 운영은 전용 DB(`AUTH_DATABASE_URL`)와 Gmail SMTP를 쓰고, 미리보기는 별도 DB 범위·별도 `AUTH_SECRET`·로그 출력 코드를 쓴다(5.3). 함께 쓰는 안은 설정이 가장 간단했지만, PR을 올리는 누구나 직원 메일 목록과 비밀번호를 읽을 수 있어 채택하지 않았다.
